# Security Audit — The Hustle Receipt

Each question is answered against the actual code, not assumptions. Where a defence holds, the exact mechanism is cited. Where there is a gap, the failure mode is described precisely and a fix is proposed.

Verdict labels:
- **HOLDS** — defence works as described
- **PARTIAL** — holds for the stated case but has a known edge
- **GAP** — real vulnerability or failure mode that needs addressing

---

## Question 1 — What if an attacker calls the success route with a fake transaction ID?

**Verdict: HOLDS with a minor information-disclosure edge case**

### What the attacker would do

Navigate to `/tip/some-slug/success?ref=i_made_this_up` without ever paying.

### What the code actually does

```ts
// app/tip/[slug]/success/page.tsx
const tip = await prisma.tip.findUnique({ where: { txRef } });
if (!tip) return false;
```

`txRef` is generated by your server — `crypto.randomUUID().replace(/-/g, "").slice(0, 32)` — and written to the database before the charge is ever created. A fake reference will not exist in the database. The lookup returns null. `verifyAndSaveTip` returns false. The user sees the error page. No tip is credited.

The attacker cannot guess a valid `txRef` because it is 32 random hex characters (128 bits of entropy). Brute-forcing it is computationally infeasible.

### The edge case: replaying a known txRef

If an attacker somehow learned a real `txRef` from a previous payment (say, by watching another user's browser URL bar), they can hit the success page with it.

```ts
if (tip.status === "success") return true;
```

The check returns `true` and shows the success screen — but the tip was already credited to the correct creator. The `creatorId` in the database is fixed at the moment the tip was created; it is not re-derived from the URL. There is no financial harm.

However, it means that knowing a `txRef` lets you confirm that a specific payment completed. There is also no validation that the slug in the URL matches the creator the tip was originally for. This is a minor **information disclosure**: an attacker who knows your `txRef` can confirm your payment by hitting the success URL for any slug, not just the right one.

This is low severity for a tipping app where amounts are public anyway, but worth knowing.

## Question 2 — What if Flutterwave's callback fires twice? (Double-credit risk)

**Verdict: HOLDS for financial correctness. PARTIAL for side effects.**

### The mechanism

```ts
// app/tip/[slug]/success/page.tsx — verifyAndSaveTip()
if (tip.status === "success") return true;
```

If the success page is loaded a second time — the user refreshes, the redirect fires twice, or a webhook retries — this line executes on the second call. The status is already "success". The function returns immediately without calling Flutterwave again or writing to the database again. The result is identical to the first call. No double-credit.

The `txRef` uniqueness constraint in the schema is the structural guarantee underneath this:

```prisma
// prisma/schema.prisma
txRef  String  @unique
```

There can only ever be one row per `txRef`. An accidental second `prisma.tip.create` with the same reference would throw at the database level — not silently succeed.

### The race condition edge

This is where it gets subtle. Consider two simultaneous requests — the browser fires the redirect and the user clicks refresh at exactly the same moment:

```
Request A: reads tip.status → "pending"
Request B: reads tip.status → "pending"   (before A has written)
Request A: calls GET /charges → "succeeded" → writes status = "success"
Request B: calls GET /charges → "succeeded" → writes status = "success"
```

Both requests call the Flutterwave verify API. Both write "success" to the database. The database write is an `UPDATE`, not an `INSERT`, and it is idempotent (setting "success" → "success" twice is the same as once). **No financial double-credit occurs.**

But both requests ran through any logic after the verification. Currently the only logic is the database write — safe. The moment you add post-payment side effects (sending a "you received a tip!" email to the creator, triggering a webhook, incrementing a separate counter), both requests would trigger them.

This is a **latent bug**. It does not cause a problem today, but it will cause a problem the first time you add notification logic without also adding a concurrency guard.

**The fix when you add side effects:**

Change the update to use an atomic conditional write that only succeeds if the current status is still "pending":

```ts
// Atomic: only succeeds if status is currently "pending"
const updated = await prisma.tip.updateMany({
  where: { txRef, status: "pending" },
  data: { status: "success" },
});

if (updated.count === 0) {
  // Another request already completed this — skip side effects
  return true;
}

// Safe to send email / fire webhook — only one request reaches here
```

`updateMany` with the `where: { status: "pending" }` condition acts as a compare-and-swap. Exactly one concurrent request will see `updated.count === 1`; all others will see `0` and skip the side effects.

## Question 3 — Is the secret key ever exposed to the client bundle?

**Verdict: HOLDS. But `lib/flutterwave.ts` lacks an explicit server-only guard.**

### Tracing every secret

| Secret | File it is read in | That file's boundary | In client bundle? |
|---|---|---|---|
| `FLW_ENCRYPTION_KEY` | `app/actions/tip.ts` | `"use server"` | No |
| `FLW_CLIENT_ID` | `lib/flutterwave.ts` | Imported only from server files | No |
| `FLW_CLIENT_SECRET` | `lib/flutterwave.ts` | Imported only from server files | No |
| `SESSION_SECRET` | `lib/session.ts` | Imported only from server files | No |
| `DATABASE_AUTH_TOKEN` | `lib/prisma.ts` | Imported only from server files | No |
| `NEXT_PUBLIC_BASE_URL` | Build-time | Intentionally public | Yes — by design |

### The "use server" import boundary

`TipForm.tsx` imports from `app/actions/tip.ts`:

```tsx
// app/tip/[slug]/TipForm.tsx  — "use client"
import { initiateTipAction, type TipActionResult } from "@/app/actions/tip";
```

This looks like it would pull the server action into the client bundle. It does not. Next.js processes `"use server"` file imports from client components by replacing them with a stub — a small object containing the action's unique ID. The actual server code, including every `process.env` read inside it, stays on the server. The `type TipActionResult` import is erased at compile time since it is a TypeScript type, not a value.

### The gap: `lib/flutterwave.ts` has no server-only guard

```ts
// lib/flutterwave.ts — no "use server" directive, no "server-only" import
const TOKEN_URL = "https://idp.flutterwave.com/...";

export async function getFlwToken(): Promise<string> {
  const clientId = process.env.FLW_CLIENT_ID;
  ...
}
```

This file is a plain module. Right now, it is only imported by `app/actions/tip.ts` and `success/page.tsx`, both server-side. But nothing prevents a future developer from importing it into a client component by mistake.

If that happened, Next.js would substitute `process.env.FLW_CLIENT_ID` with `undefined` at build time (non-`NEXT_PUBLIC_` variables are not inlined into client bundles), so the actual credential value would not leak. However, the module code itself would be bundled and visible to anyone who inspects the JavaScript.

**The fix:**

Add one import to the top of the file:

```ts
// lib/flutterwave.ts
import "server-only";
```

The `server-only` package (included with Next.js) throws a build-time error if this module is ever imported in a client component. It turns a runtime silent failure into an immediate compile error.

## Question 4 — What if the verify API call fails?

**Verdict: GAP. A Flutterwave outage at the moment of verification can permanently misclassify a successful payment.**

### What the code does on a network error

```ts
// app/tip/[slug]/success/page.tsx — verifyAndSaveTip()
try {
  const res = await flwFetch(`/charges/${tip.flwTxId}`);
  json = await res.json();
} catch {
  return false;
}
```

If `flwFetch` throws — DNS failure, timeout, TLS error — the catch fires, returns false, and the tip remains in the database as `"pending"`. The user sees the "payment not completed" error page. They paid. The creator does not see the tip. There is no retry and no notification.

### The more dangerous failure: non-2xx response with valid JSON

If Flutterwave's API returns a `500 Internal Server Error` with a JSON body like:

```json
{ "status": "error", "message": "Something went wrong" }
```

`res.json()` succeeds (the body is valid JSON). Execution falls through the try/catch into:

```ts
if (
  json.data?.status !== "succeeded" ||
  json.data?.reference !== txRef
) {
  await prisma.tip.update({
    where: { txRef },
    data: { status: "failed" },
  });
  return false;
}
```

`json.data` is undefined. `undefined?.status` is undefined. `undefined !== "succeeded"` is true. The condition fires. The tip is updated to `"failed"`. The user sees the error page.

A transient Flutterwave server error — something that would resolve in seconds — permanently marks a successful payment as failed in your database. The charge exists on Flutterwave's side. The money moved. Your records say otherwise.

**Note:** because the idempotency check only guards against `"success"` — there is no equivalent guard for `"failed"` — a user who refreshes the success page after a failed verification would re-run the Flutterwave API call. If the transient error has cleared, the second attempt would succeed. The tip would be correctly marked. This accidental retry behaviour mitigates the worst outcome, but it depends on the user refreshing, which is not guaranteed.

### The fix

Distinguish between three outcomes:

```ts
async function verifyAndSaveTip(txRef: string): Promise<boolean> {
  const tip = await prisma.tip.findUnique({ where: { txRef } });
  if (!tip) return false;
  if (tip.status === "success") return true;
  if (!tip.flwTxId) return false;

  let res: Response;
  let json: Record<string, unknown>;

  try {
    res = await flwFetch(`/charges/${tip.flwTxId}`);
    json = await res.json() as Record<string, unknown>;
  } catch {
    // Network failure — leave tip as "pending" so a retry can succeed
    return false;
  }

  // Flutterwave API itself returned an error — do not mark as failed
  // A transient 5xx should not permanently poison the record
  if (!res.ok) return false;

  if (
    (json.data as Record<string, unknown>)?.status !== "succeeded" ||
    (json.data as Record<string, unknown>)?.reference !== txRef
  ) {
    // Flutterwave explicitly confirmed failure or mismatch — safe to mark failed
    await prisma.tip.update({ where: { txRef }, data: { status: "failed" } });
    return false;
  }

  await prisma.tip.update({ where: { txRef }, data: { status: "success" } });
  return true;
}
```

The key change: `if (!res.ok) return false` — a Flutterwave server error leaves the record as "pending" rather than poisoning it to "failed". The user still sees an error page, but a refresh (or a future reconciliation job) can resolve it correctly.

## Question 5 — Are amounts validated server-side, or only on the client?

**Verdict: HOLDS. Server-side Zod validation is the authoritative check.**

### The client-side constraints

The form in `TipForm.tsx`:

```tsx
<input
  name="amount"
  type="number"
  required
  min={100}
  step={50}
/>
```

`min`, `step`, and `required` are HTML attributes. They are enforced by the browser. They are not enforced by anything else. An attacker using curl, Postman, or browser DevTools can send any value they choose and the HTML validation will never run.

### The server-side check

Inside `initiateTipAction` — which carries `"use server"` and runs on your server — the first thing that happens after reading the form data is:

```ts
// app/actions/tip.ts
const parsed = tipSchema.safeParse(raw);
if (!parsed.success) {
  return { errors: parsed.error.flatten().fieldErrors };
}
```

And the schema:

```ts
// lib/validations.ts
amount: z.coerce
  .number()
  .int("Amount must be a whole number")
  .min(100, "Minimum tip is ₦100")
  .max(10_000_000, "Amount too large"),
```

`z.coerce.number()` converts the form string to a JavaScript number. `.int()` rejects decimals. `.min(100)` rejects anything below ₦100. `.max(10_000_000)` rejects impossibly large values. This runs before any API call, before any database write.

If an attacker sends `amount=50`, the parsed amount is 50, which fails `min(100)`. The action returns `{ errors: { amount: ["Minimum tip is ₦100"] } }` and stops. Flutterwave is never called. Nothing is saved.

If an attacker sends `amount=-5000`, it fails `min(100)`. Same result.

If an attacker sends `amount=99999999`, it fails `max(10_000_000)`. Same result.

The amount that reaches Flutterwave's charge API is always `parsed.data.amount` — the Zod-validated value — never the raw form string.

## Additional Findings

These were not in the original questions but emerged from reading the code.

### Finding A — `status` is an unconstrained string in the schema

```prisma
// prisma/schema.prisma
status  String  @default("pending")
```

There is no enum or check constraint. The only valid values in the application logic are `"pending"`, `"success"`, and `"failed"`. But the database will accept `"PENDING"`, `"bananas"`, or any other string without complaint. A bug that writes `"sucess"` (typo) would silently create records that no status check would ever match.

**Fix:** Define the valid statuses as a TypeScript union and use it in a helper, or switch to a Prisma enum:

```prisma
enum TipStatus {
  pending
  success
  failed
}

model Tip {
  status  TipStatus  @default(pending)
  ...
}
```

### Finding B — If the server crashes between charge creation and saving `flwTxId`, the tip is permanently unresolvable

```ts
// app/actions/tip.ts — two separate database calls
await prisma.tip.create({ data: { ..., status: "pending" } });
// ← if the process crashes here
await prisma.tip.update({ where: { txRef }, data: { flwTxId: chargeId } });
```

If the server dies between these two lines — a Vercel cold-start timeout, an unhandled exception in charge creation, an OOM — the tip row exists as "pending" with no `flwTxId`. When the success page runs:

```ts
if (!tip.flwTxId) return false;
```

It exits early. The payment cannot be verified. The tip is permanently stuck. There is no reconciliation path.

This is difficult to fix cleanly without a database transaction that spans the API call (not possible with a remote API). A practical mitigation is to write the `flwTxId` as part of the initial `tip.create` — which means creating the charge before saving the tip, and using a try/catch to handle charge failure. Alternatively, a background reconciliation job that queries Flutterwave for any `pending` tips older than N minutes provides an escape hatch.

### Finding C — No rate limiting on tip submission

Every form submission calls three Flutterwave API endpoints in sequence. There is no rate limiting, no CAPTCHA, and no per-IP throttle. An attacker who wants to exhaust your Flutterwave API quota — or trigger rate limit errors that degrade the service for real users — can simply spam the tip form.

This is a real operational risk, not just theoretical. Flutterwave enforces their own rate limits; hitting them returns errors that real users would also receive.

**Fix:** Add rate limiting at the Vercel edge or in the Server Action using a package like `@upstash/ratelimit` with a Redis backend (Upstash offers a free tier). Limit by IP address: e.g., 10 tip attempts per IP per 15 minutes.

### Finding D — The production PIN is hardcoded

```ts
// app/actions/tip.ts
const encPin = await encryptCardField("12345", encKey, nonce);
```

This is documented as sandbox-only and works for testing. In production, Nigerian bank cards that require PIN will reject the wrong PIN and the charge will fail at the PIN step. This is a launch blocker, not a security vulnerability — the failure is visible immediately — but it needs a second form step added before going live with real credentials.

### Finding E — `lib/flutterwave.ts` should be marked server-only

Covered in Question 3. The absence of `import "server-only"` is not currently a bug — no client component imports this module — but it is one misdirected import away from becoming one. One line prevents the class of error entirely.
